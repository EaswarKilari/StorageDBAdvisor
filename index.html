What is the main job this database has to do day to day?

What do these mean?
Transactional app (OLTP)
Lots of small reads and writes from an application — sign-ups, orders, profile updates. The everyday "backend database" case.
Analytics / reporting (OLAP)
Scanning and aggregating huge numbers of rows for dashboards and reports (sums, averages, trends) rather than touching single records.
Mixed (HTAP)
You need both at once: live transactions and analytics on the same data without copying it elsewhere.
Caching / sessions
Temporary, fast-access data (logged-in sessions, hot results) that can be rebuilt if lost.
Full-text search
Searching text by keywords and relevance, like a site search box or log search.
Time-series / metrics
Timestamped data arriving continuously — server metrics, IoT sensors, stock ticks.
Key-value at scale
Simple "look up a value by its key" access, but at very high volume across many machines.
Connected data / graph
Data that is mostly about relationships — social networks, recommendations, fraud rings — where you traverse links.
Vector / similarity search
Finding "nearest" items by meaning using AI embeddings — semantic search, recommendations, RAG for LLMs.

How do you want your data shaped and organized?

What do these mean?
No preference
Let the match decide; don't filter by data shape.
Relational (tables)
Rows and columns with a fixed schema and relationships — classic spreadsheets/SQL tables.
Document (JSON-like)
Flexible, nested records (like JSON). Each record can differ; great for evolving schemas.
Key-value
The simplest model: a key maps to a blob/value. Extremely fast, minimal structure.
Wide-column
Rows that can have millions of dynamic columns, grouped into families; good for huge sparse datasets.
Columnar
Stores each column together on disk so analytics scans read only the columns they need, with strong compression.
Time-series
Specialized for timestamped points, with time-based partitioning and retention built in.
Graph (nodes & edges)
Data stored as nodes connected by relationships; ideal for traversing networks of links.
Vector (embeddings)
Stores numeric vectors (AI embeddings) and finds the most similar ones quickly.

Will your system mostly read existing data, mostly write new data, or both evenly?

What do these mean?
Read-heavy
Most operations fetch data that already exists (e.g., a content site read far more than it's updated). Favors read-optimized engines like B-trees.
Balanced
A roughly even mix of reads and writes — typical for many apps.
Write-heavy
You ingest large volumes of new data constantly (logs, events, sensors). Favors write-optimized engines like LSM-trees.

How strict must the database be about everyone always seeing the latest, correct data?

What do these mean?
Strict ACID transactions
Guarantees that multi-step changes fully succeed or fully fail, and reads always see committed, correct data. Essential for money, inventory, bookings.
Tunable is fine
You can trade some strictness for speed/availability on a per-operation basis (e.g., require a majority of replicas to agree).
Eventual consistency is OK
Replicas may briefly disagree and "catch up" shortly after. Fine for likes, view counts, caches where a small delay is harmless.

Can one server hold your data and traffic, or do you need to spread across many machines?

What do these mean?
Single node is fine
One machine (plus maybe a backup replica) can comfortably handle your data size and load. Simpler to run.
Needs horizontal scale
Data/traffic is too big for one machine, so it must shard/replicate across a cluster and grow by adding nodes.

Where and how do you want to run the database?

What do these mean?
No preference
Don't filter by how it's run.
Embedded / in-process
The database runs inside your application as a library — no separate server to install (e.g., SQLite, DuckDB). Great for apps, devices, and local tools.
Self-hosted server
You install and operate the database on your own machines/VMs/containers. Full control, but you handle backups, upgrades, and scaling.
Managed cloud service
A cloud provider runs it for you (e.g., DynamoDB, Snowflake). Less operational work; you pay for convenience and lose some low-level control.
